## 알아두면 시간 아끼는 것들

`middleware`**가 아니라** `proxy`**.** Next 16이 `middleware` 파일 규약을 deprecate하고
이름을 바꿨습니다. API는 같습니다. Supabase 공식 문서는 아직 `middleware`로 적혀 있으니
문서를 볼 때 헷갈리지 마세요.

**세션 판정은** `getClaims()`**.** `getSession()`은 서버에서 신뢰하지 않습니다.

**anon 키는 publishable key(**`sb_publishable_...`**)를 씁니다.**
환경변수 이름은 기획서 §9대로 `NEXT_PUBLIC_SUPABASE_ANON_KEY` 유지.

**익명 키로 테이블을 조회하면** `200 []`**가 정상입니다.** 정책이 전부
`to authenticated`라 RLS가 아무것도 주지 않습니다. 행을 눈으로 보려면
`service_role` 키가 필요한데, `supabase projects api-keys`는 새 `sb_secret_...`을
마스킹해서 줍니다 — 레거시 `service_role` JWT를 쓰거나 대시보드에서 복사하세요.

**쿼리 문법만 확인할 때는 익명 키가 오히려 편합니다.** RLS로 `[]`가 오지만 문법이
틀리면 400이 옵니다. **임베드한 필터가 정말 자식 테이블에 걸리는지**도 없는 컬럼을
넣어보면 압니다 — `passage.nope=is.null` → `column passage_1.nope does not exist`.

**Supabase가 실제로 들고 있는 OAuth 값 확인법.**

```
GET {SUPABASE_URL}/auth/v1/authorize?provider=google&redirect_to=...
→ 302 Location에 client_id, redirect_uri, scope가 그대로 들어 있음
```

세션 1-c에서 구글 client ID가 앞부분(`1974351245-`)이 잘린 채 저장돼 있어
`invalid_client`가 났습니다. 구글 client ID는 항상
`프로젝트번호-무작위문자.apps.googleusercontent.com` 형태입니다.

`toy` **프로젝트를 가리키고 있지 않은지 확인.**
`cat supabase/.temp/project-ref` → `ccfgjaxaylwwdfsspdys`

**로그인이 필요한 경로를 스크립트로 검증하는 법.** 구글 OAuth는 스크립트로 못
돌리지만, 검증용 계정을 만들면 됩니다. 세션 3에서 API 전체를 이렇게 확인했습니다.

```
1. service_role로 계정 생성   POST /auth/v1/admin/users  {email, password, email_confirm:true}
2. 비밀번호로 로그인          POST /auth/v1/token?grant_type=password   → access_token
3. 쿠키로 만들어 curl에 붙임  sb-<project-ref>-auth-token=base64-<base64(세션 JSON)>
4. 끝나면 계정 삭제           DELETE /auth/v1/admin/users/<id>
```

`shelf_item`·`profile`은 `auth.users` cascade로 같이 사라지고 `book`은 남습니다
(공용 마스터라서 정상입니다). `UID`**를 셸 변수 이름으로 쓰지 마세요** — zsh 예약
변수라 대입이 실패합니다.

**공개 버킷은 CDN이 캐시합니다.** 같은 경로에 파일을 덮어써도 공개 URL이 한동안
옛 파일을 줍니다. 세션 3에서 이걸 모르고 버그로 착각했습니다. 실제 내용을 보려면
인증 경로(`/storage/v1/object/cover/...` + service_role)나 쿼리스트링으로 캐시를
피하세요.

`supabase db dump`**는 도커가 필요합니다.** 적용된 스키마를 원격에서 대조할 때는
Management API의 query 엔드포인트로 직접 조회하세요 (세션 2에서 그렇게 했습니다).

**Next 16** `dev`**는 데몬으로 뜹니다.** 실행한 명령이 먼저 끝나고 서버는 남습니다.
두 번 실행하면 `Another next dev server is already running`과 함께 PID를 알려줍니다.
로그는 `.next/dev/logs/next-development.log` (브라우저 콘솔 경고까지 들어옵니다).
`pkill -f "next dev"`**는 이미 떠 있던 서버까지 잡습니다** (세션 4에서 한 번
그랬습니다). 포트로 골라 죽이세요.

`next/font`**로 한글 폰트를 쓸 때** `subsets`**를 지정하면 안 됩니다.** next/font가 아는
서브셋은 `latin` / `latin-ext`뿐입니다. 지정하면 **빌드는 통과하고 한글만 시스템
폰트로 조용히 떨어집니다.** 비워두면 한글 서브셋까지 내려받습니다 — 대신
unicode-range가 246개로 쪼개지므로 `preload`는 끕니다.

**판단이 필요했던 지점**

- **표지 크기·열 배치**를 `/test`에서 단계별(160→200→240→…→320px, 폭 720/960/1200,
  6열/4열)로 실물 비교해 사용자가 선택: 상세 표지 **240**, 상세 컨테이너 **720 고정**
  (1200은 "너무 넓다"), 책장은 **큼지막(255)·반응형 열**.
- **소개 위치·물성** — 오른쪽 칼럼 안(출판사·쪽수 아래), 산세리프 보조색. 길면 5줄
  clamp(사용자가 "긴 시안 위치보다 더 내려오면 제한" 지시 → 표지 높이 안에 가두는
  규칙으로 구현).
- **읽기 폭 vs 갤러리 폭 분리** — "모든 화면 720"을 깨되 문장 화면(상세·밑줄)은 720을
  지키고 책장만 넓힘. 네비는 전체 폭으로 두 폭을 잇는 프레임.

**어긋난 부분**

- 없음(문서를 코드와 함께 갱신). 판형·무게·출간일 제거는 사용자가 "애초에 잘못된
  결정"이라 해 어긋남이 아니라 §5 정정으로 처리. 표지 148px 상한 폐기·720 단일폭
  폐기도 사용자 승인 아래 design.md를 고쳐 정합성 유지.
- 남은 검토: 네비(전체 폭)와 720 읽기 콘텐츠의 왼쪽 정렬 어긋남이 거슬리는지는
  실사용에서 판단.

**후속 조정 (같은 날)**

- **책장 최대 4열로.** 앞서 auto-fill(무제한 열)이 넓은 모니터에서 열이 너무 많이
  생김. 사용자 지시로 **최대 4열**(`grid-cols-1 → min-[440px]:2 → min-[900px]:4`,
  컨테이너 max-w 1600)로 바꿈. 셀이 유동(`1fr`)이라 **넓으면 4권이 폭을 채우게 표지가
  커지고, 좁으면 2·1열로 줄며 작아짐.** 판형의 크기 차이는 고정 px(SCALE) 대신
  **셀 폭 대비 %**(`box.width/148 × 셀폭`)로 살려 열 수가 바뀌어도 문고본/사진집
  비율이 유지됨. 슬롯 고정 높이를 버리고 셀 stretch + 표지 하단 정렬로 바닥을 맞춤.
- **오늘의 밑줄 제거.** 표지를 크게 쓰니 책장 맨 위 한 장의 자리가 애매해짐 →
  사용자 지시로 뺌. `todays-underline.tsx`는 남겨둠(로직 보존), 넓은 책장에서
  어떻게 보일지 정하면 복귀. 기획서 §5·design.md·이 표에 반영.

## 세션 N — 밑줄·상세 폭 재설계 (2026-08-05)

읽기 폭(720)과 갤러리 폭이 안 맞아 상세·밑줄이 넓은 화면에서 "가운데 좁은 기둥"으로
떠 보이던 문제. 폭을 통일하는 대신 **컨테이너는 화면 폭, 글줄만 720**으로 뒤집음.

**이번에 한 것**

- **밑줄 목록 `/underlines`.** 가운데 720 카드 스택 → **화면 폭 accent 밴드** 스택.
  밑줄마다 그 책 색이 화면 끝까지 흐르고 글줄만 읽기 폭(왼쪽 거터). 스크롤하다 색이
  바뀌면 책이 바뀐 것(기획서 §5가 원하던 것).
- **책 상세 `/shelf/[id]`.** 720 단일 칼럼 → **펼침 2단**. lg↑에서 왼쪽(표지·정보·
  상태·별점·리뷰, 종이, `sticky`) | 오른쪽(밑줄, accent **필드**, 화면 오른쪽 끝까지).
  좁은 화면은 접혀 위→아래로 쌓임. **밑줄 사이 직선 구분선 제거** — 손그림 밑줄+쪽수가
  경계를 대신(화면의 선은 손그림 한 종류). **책 소개 제거.** 긴 제목 전부 노출.
- **accent 색을 카드 → 컨테이너로 이동.** `passage-card.tsx`는 이제 **내용만** 그림
  (배경·좌우여백·링크 제거). 새 `passage-band.tsx`가 밑줄 목록의 밴드를 두름. 상세는
  오른쪽 필드가 색을 두름. `passage-item.tsx`(고치기)·`add-passage.tsx`(추가)에서
  각자 그리던 accent 배경·패딩을 걷어냄 — 투명 위로 필드 색이 비쳐 "색 위에 쓰는"
  감각은 유지. `todays-underline.tsx`(휴면)도 PassageBand로 맞춰 컴파일 유지.
- 문서 갱신: `design.md` §레이아웃(전체 폭 컨테이너+글줄 720)·§책 상세(펼침 2단)·
  §문장 카드(색은 컨테이너가, 28px 규칙 범위 정정)·§하지 말 것(글줄만 720).

**남은 것**

- **실제 앱 화면 확인.** 전 경로가 로그인 보호 + Supabase 데이터라 자동으로 못 띄움.
  빌드·린트·승인된 프리뷰(HTML)로 검증. 로그인해 밑줄/상세를 눈으로 확인 필요:
  특히 왼쪽 sticky 동작, 오른쪽 필드가 우측 끝까지 흐르는지, 초광폭에서 색 면 과다,
  밑줄 1개뿐인 책의 필드가 휑한지.
- 프리뷰 파일 3종(`design-preview*.html`)은 확인용 — 정리(삭제) 대상.
- 상세 2단 breakpoint는 `lg`(1024px)로 잡음. 실사용에서 좌 300~360+우 밑줄이
  충분히 벌어지는지 보고 조정 가능.

**판단이 필요했던 지점**

- **폭 처리 3안(밑줄) 프리뷰로 비교** → 사용자 ② "전체 폭 accent 밴드" 선택.
