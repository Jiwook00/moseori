Create GitHub issues from the current conversation, a pasted task list, or the diff. Usage: /issue-new [작업 목록]

완벽한 기획이 아니라 **나중에 작업할 때 문맥을 파악할 수 있는 정도**로 쓴다.
해결책을 설계하지 않는다. 판단이 필요한 건 "정할 것"에 남기고, 결정은 이슈를 작업할 때 한다.

## Steps

1. **컨텍스트 수집**

   다음을 함께 확인:
   - `$ARGUMENTS` 또는 현재 대화에서 나온 문제·요구사항
   - `git diff HEAD` (변경사항이 있다면)
   - `gh issue list --state open` — 겹치거나 관련된 이슈
   - `docs/기획서.md` §2 "안 하는 것" — 여기에 걸리는 요구가 있는지

2. **이슈 단위로 나누기**

   - 한 이슈 = 한 문제. 같은 화면·같은 흐름을 건드리는 건 묶고, 한 항목 안의 서로 다른 문제는 나눈다
   - 라벨: 깨진 동작 → `type: bug`, 기능·흐름 추가나 변경 → `type: feature`, 문서·설정·정리 → `type: chore`. `phase:` 라벨이 있으면 추가
   - "안 하는 것"에 걸리면 만들지 말지 판단하지 말고, 해당 이슈 "정할 것" 첫 항목에 **범위 확인**으로 적고 사용자에게도 알린다

3. **초안 보여주기**

   먼저 전체를 표로:

   | #   | 제목 | 라벨 | 관련 |
   | --- | ---- | ---- | ---- |

   이어서 각 본문:

   ```
   제목: <한국어, 50자 이내>
   라벨: <type: bug / type: feature / type: chore 중 하나> + <phase: 라벨 있으면 추가>

   ## 배경
   (지금 어떤지, 왜 불편하거나 필요한지. 사용자가 말한 예시는 살린다)

   ## 정할 것
   (판단이 필요한 지점과 선택지. 없으면 섹션째 뺀다)

   ## 할 일
   - [ ] 항목

   ## 참고
   (관련 이슈 #N, 기획서 절, 파일. 없으면 뺀다)
   ```

   원인을 추측했다면 "(추정)"이라고 표시한다.

4. **확인 요청**

   > 이대로 생성할까요? (y / edit / cancel)
   - `y` → 본문을 스크래치패드 파일에 쓰고 `gh issue create -t "..." -l <라벨> -F <파일>`로 하나씩 생성
   - `edit` → 수정할 부분(나누기·묶기·문구)을 물어보고 다시 보여준 뒤 재확인
   - `cancel` → 중단

5. **연결하고 마무리**

   - 같이 만든 이슈끼리 서로 참조하는 곳은 번호가 정해진 뒤 `gh issue edit N -F <파일>`로 `#N`을 채운다
   - 생성된 이슈를 표(번호·제목·라벨·URL)로 보여준다
